# ⚡ AI-Powered Energy Consumption Forecasting System

A beginner-friendly, GitHub-ready machine-learning project that forecasts hourly electricity consumption from historical usage patterns. It includes a reproducible simulated dataset, time-aware feature engineering, a Random Forest model, chronological evaluation, saved charts, a 24-hour recursive forecast, a Flask prediction API, and an optional Streamlit dashboard.

> **Dataset transparency:** The default dataset is synthetic demo data generated by this project. It is designed to demonstrate a workflow and is **not** actual utility-meter or corporate data. Replace it with an appropriately licensed real dataset before making real-world performance claims.

## Problem statement
Energy use changes with hour, weekday/weekend patterns, seasons, and recent demand. Forecasting can help building operators plan schedules, investigate peak demand, and explore energy-efficiency strategies. This project demonstrates the analytics workflow; it does not control a grid or guarantee savings.

## Features
- Generates 2 years of hourly simulated energy data when no CSV exists.
- Cleans timestamps, duplicates, missing values, and invalid consumption values.
- Creates hour/day/month/weekend, lag, and rolling-average features.
- Trains a Random Forest with a chronological 80/20 split (not a random split).
- Reports MAE, RMSE, R² and compares MAE with a previous-hour baseline.
- Saves test predictions, a recursive next-24-hour forecast, metrics, and PNG charts.
- Offers a Flask JSON API and an optional Streamlit dashboard.

## Architecture
```text
Hourly CSV (synthetic or your own)
          |
          v
Validation + cleaning + hourly resampling
          |
          v
Time features + lag/rolling features
          |
          v
Chronological train/test split
          |
          v
Random Forest model + persistence baseline
          |
          +----> MAE / RMSE / R² (outputs/metrics.json)
          +----> Actual-vs-predicted chart (images/)
          +----> Next 24-hour forecast (outputs/)
          +----> Flask API (app.py)
          +----> Streamlit dashboard (dashboard.py)
```

## Run the API
In one terminal, train the model first and then:
```bash
python app.py
```
Open `http://127.0.0.1:5000/` or `http://127.0.0.1:5000/health`.

`POST /predict` JSON body (all fields are required):
```json
{
  "hour": 14,
  "day_of_week": 2,
  "month": 10,
  "is_weekend": 0,
  "lag_1": 108.4,
  "lag_24": 101.7,
  "lag_168": 97.3,
  "rolling_mean_24": 103.2
}
```
Use Postman or curl to send JSON to `http://127.0.0.1:5000/predict`. The values above are examples only.

## Use a real dataset
Keep the required columns `timestamp` and `energy_kwh`; an optional `temperature_c` column is accepted but not currently used by the model. Timestamps should represent a consistent hourly time series. Back up the synthetic CSV before replacing it. The loader sorts, deduplicates, resamples hourly, and interpolates short gaps. Avoid mixing meters or units in one series.

## Evaluation notes
- MAE: average absolute prediction error, in kWh.
- RMSE: penalizes larger errors more heavily, in kWh.
- R²: proportion of target variation explained relative to a constant-mean baseline; can be negative.
- Previous-hour baseline: a simple reference, not a competing trained model.
- A chronological split better reflects forecasting than a random split. Lagged features are built from prior observations.

## Project limitations and next steps
- Synthetic data cannot establish real operational performance.
- Weather is generated for realism but not included in the model yet.
- Recursive multi-step forecasts can accumulate error.
- Potential extensions: weather/calendar features, seasonal naive baseline, model tuning, prediction intervals, drift monitoring, tests, and a deployment container.
